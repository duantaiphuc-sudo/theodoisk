1. Vấn đề lớn nhất của mainnew_sync.py: Firestore bị ghi quá thường xuyên
Tôi đã kiểm tra trực tiếp v4.0/mainnew_sync.py trên nhánh main.
Nguyên nhân chính: FirebasePublisher._loop() hiện ghi dữ liệu lên Firestore theo chu kỳ 2 giây, bất kể dữ liệu tư thế, nhịp tim hay SpO₂ có thực sự thay đổi hay không.
Trong mã nguồn:
FIREBASE_PUSH_INTERVAL = 2.0
Cơ chế hiện tại:
•	FirebasePublisher.update() nhận trạng thái mới từ vòng lặp chính.
•	FirebasePublisher._loop() lấy snapshot mới nhất rồi gọi Firestore.
•	Sau khi ghi thành công, chương trình đặt thời điểm ghi tiếp theo bằng now + FIREBASE_PUSH_INTERVAL.
•	Mỗi lần ghi lại cập nhật timestamp bằng SERVER_TIMESTAMP, nên ngay cả khi các chỉ số không thay đổi, tài liệu vẫn được cập nhật.
Đây là ghi theo chu kỳ (periodic publishing), chưa phải ghi theo sự kiện (event-driven publishing).

Logic Publisher cần sửa
Tôi đề xuất tách quyết định có cần ghi thành một hàm riêng, đại ý:
def should_publish(current, previous, elapsed):
    if previous is None:
        return "INITIAL"

    important = (
        "posture_status",
        "posture_label",
        "is_in_zone",
        "tracking_active",
        "userId",
    )

    if any(current.get(k) != previous.get(k) for k in important):
        return "STATE_CHANGED"

    if (current["bpm"] > 0) != (previous["bpm"] > 0):
        return "HR_VALIDITY_CHANGED"

    if (current["spo2"] > 0) != (previous["spo2"] > 0):
        return "SPO2_VALIDITY_CHANGED"

    if elapsed >= 10:
        if abs(current["bpm"] - previous["bpm"]) >= 3:
            return "HR_CHANGED"

        if abs(current["spo2"] - previous["spo2"]) >= 1:
            return "SPO2_CHANGED"

    if elapsed >= 60:
        return "HEARTBEAT"

    return None
Đây là logic tham khảo, chưa phải đoạn thay thế hoàn chỉnh. Khi tích hợp thật cần tách thời điểm gửi sinh hiệu và heartbeat, kiểm tra quyền phiên khuôn mặt trước khi ghi, chỉ cập nhật previous sau khi Firestore xác nhận thành công và tránh phát quá nhiều lần nếu trạng thái nhấp nháy.
5. Một vấn đề quan trọng khi giảm Firestore: lịch sử Supabase
Hiện tại, App.tsx gọi insertTelemetryToSupabase() từ luồng nhận telemetry trên web. Code có điều kiện ghi khi có cảnh báo, đổi tư thế, thay đổi sinh hiệu hoặc sau khoảng 5 giây.
Điều đó gây ra hai hệ quả:
Thứ nhất, nếu giảm số gói Firestore xuống một gói/phút, web không còn đủ dữ liệu đầu vào để ghi lịch sử với độ phân giải 5 giây.
Thứ hai, khi không có trình duyệt đang mở, cơ chế ghi lịch sử từ handleIncomingTelemetry() không chạy.
Đối với khóa luận, tôi đề xuất về lâu dài chuyển phần ghi lịch sử sang một tiến trình độc lập trên Pi hoặc backend. Pi có thể lưu sự kiện và số đo hợp lệ vào SQLite cục bộ, rồi gửi lô dữ liệu định kỳ qua API được xác thực. Như vậy, Firestore chỉ giữ trạng thái realtime, còn lịch sử không phụ thuộc vào việc có mở dashboard hay không.

7. Thứ tự sửa để giảm chi phí mà ít ảnh hưởng hoạt động
1
Sửa FirebasePublisher trước
Thêm change detection + heartbeat 60 giây, giữ phản hồi nhanh khi trạng thái thay đổi. Không cần thay kiến trúc AI hoặc cảm biến.
2
Loại bỏ ghi trùng trên web
Hợp nhất hai heartbeat 12 giây, tránh updateUserRealtimePresence() trên mọi gói telemetry và kiểm tra việc ghi web_display/current.
3
Tách lưu lịch sử khỏi luồng realtime
Giữ Firestore cho trạng thái tức thời; dùng Supabase cho lịch sử theo sự kiện hoặc lấy mẫu có kiểm soát.
4
Kiểm thử lại
Đo số lượt ghi/đọc trong Firebase Console, độ trễ cảnh báo, mất mạng, dữ liệu stale và khả năng tiếp tục đồng bộ.
Có nên chuyển sang Firebase Realtime Database?
Chưa cần chuyển ngay.
Realtime Database tính phí chủ yếu theo dung lượng lưu trữ và dữ liệu tải xuống, thay vì số document read/write như Firestore Standard. Nó có thể phù hợp hơn với dữ liệu thay đổi thường xuyên, nhưng chưa chắc rẻ hơn trong mọi trường hợp vì còn phụ thuộc số thiết bị, kích thước gói và số người đang theo dõi.
